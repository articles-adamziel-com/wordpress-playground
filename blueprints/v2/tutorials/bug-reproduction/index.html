Create a one-click bug or pull-request reproduction

A useful reproduction gives every reviewer the same runtime, code, data, starting URL, and steps to follow. Blueprint v2 can open that test case with one click in a browser, while the same committed file runs headlessly in CI.

What you will build​

  • Exact WordPress and plugin releases on a selected PHP runtime line.
  • Minimal content that states one expected and one actual result.
  • Short, numbered steps another person can follow without extra context.
  • A visible environment marker generated by a small inline mu-plugin.
  • A share URL that starts the example directly in Playground.
  • A headless command suitable for a pull request or continuous integration.

Prerequisites​

  • A minimal sequence that reproduces the behavior on a fresh site.
  • Exact released versions, or the full commit SHA of code under review.
  • A public, CORS-readable URL if reviewers will load the JSON in a browser.
  • Node.js for local and CI execution with the Playground CLI.

Run the finished example​

Run in Playground

The example opens /bug-reproduction/ and reports WordPress 6.8.3, the PHP 8.3 runtime line, and Hello Dolly 1.7.2 as active. Its report page includes Steps to reproduce, Expected, and Actual sections. Replace that sample report and dependency with the smallest state that exposes the real problem. After it opens, use Dock → Blueprint to inspect or edit the JSON.

Reproduce the example​

This sample checks that the selected runtimes and plugin are the inputs you actually receive:

  1. Open Run in Playground in a fresh browser tab.
  2. Wait for /bug-reproduction/ to load.
  3. Under the page title, read the reported WordPress, PHP, and Hello Dolly versions and the plugin's activation state.
  4. Compare them with the expected WordPress 6.8.3, PHP 8.3, and active Hello Dolly 1.7.2 values.
  5. Confirm the page contains Steps to reproduce, Expected, and Actual sections.

For a real bug, replace that sequence with the shortest interaction that exposes the problem. Include those numbered steps in the issue as well as in the reproduction page whenever possible.

Customize the example​

Example fieldReplace it withCheck after a clean run

Make the report page follow the same order a reviewer will use: Steps to reproduce, Expected, then Actual. Keep each step observable and remove any step that does not contribute to the result.

1. Pin every input that defines the result​

The example uses exact WordPress and plugin releases, plus a selected PHP runtime line:

"phpVersion": "8.3",
"wordpressVersion": "6.8.3",
"plugins": [
	{
		"source": "hello-dolly@1.7.2",
		"active": true,
		"ifAlreadyInstalled": "skip"
	}
]

Do not use latest, a moving branch, or an unversioned WordPress.org slug in a long-lived bug report. Those inputs can change without changing the JSON.

For a plugin or theme built directly from Git, use the full commit SHA:

"plugins": [
	{
		"source": {
			"gitRepository": "https://github.com/acme/example-plugin",
			"ref": "4f86d3f04b47e86a9802a58e6c7aef2f3cb92f55",
			"pathInRepository": "plugin"
		},
		"targetDirectoryName": "example-plugin",
		"active": true
	}
]

A pull-request ref is convenient while a review is moving, but it is mutable. Record the full head commit in a reproduction that must still mean the same thing after the pull request changes or closes. Git sources install committed files only; point to a built artifact when the project requires a build step.

2. Declare only representative state​

The example turns on debug constants, creates one page, and registers one inline shortcode. This is enough to make the runtime visible and keep the expected-versus-actual report beside the test content.

For a real issue:

  1. Remove unrelated plugins, themes, options, users, and content.
  2. Preserve the exact activation state that triggers the problem.
  3. Use stable slugs and an explicit landingPage.
  4. State one observable expected result and one observable actual result.
  5. Keep any interaction after boot short enough to repeat in a review.

The inline mu-plugin is executable PHP. Use it only for setup that cannot be expressed as ordinary site state, and keep it small enough to review in the JSON. Use final setup steps only when the reproduction genuinely needs command-like work after the top-level site fields.

3. Commit the example and make a browser share URL​

Host the JSON at an immutable URL. A raw GitHub URL should contain the full commit SHA, not main or trunk. This snippet prints the share URL so you can open or paste it:

const commit = '4f86d3f04b47e86a9802a58e6c7aef2f3cb92f55';
const blueprintUrl = ['https://raw.githubusercontent.com/acme/example-plugin', commit, 'tests/bug-reproduction.json'].join('/');

const shareUrl = new URL('https://playground.wordpress.net/');
shareUrl.searchParams.set('blueprint-url', blueprintUrl);
console.log(shareUrl.href);

Open shareUrl in a signed-out browser before posting it. The JSON and every adjacent remote asset need normal browser fetch and CORS access. For private or binary inputs, prefer an attached, reviewable bundle rather than embedding credentials in a URL.

4. Run the same example headlessly​

Execute it locally without starting a web server:

npx @wp-playground/cli@latest run-blueprint \
	--blueprint=./tests/bug-reproduction.json

For CI, install the CLI as a development dependency and commit the resulting lockfile. That pins the runner version used by future checks:

npm install --save-dev --save-exact @wp-playground/cli
npm exec -- wp-playground-cli run-blueprint \
	--blueprint=./tests/bug-reproduction.json

Then run the same command after npm ci. For example:

name: Blueprint reproduction

on:
    pull_request:

jobs:
    run-blueprint:
        runs-on: ubuntu-latest
        steps:
            - uses: actions/checkout@v4
            - uses: actions/setup-node@v4
              with:
                  node-version: 22
                  cache: npm
            - run: npm ci
            - run: >-
                  npm exec -- wp-playground-cli run-blueprint
                  --blueprint=./tests/bug-reproduction.json

The command checks schema validation, source resolution, installation, and setup. Keep assertions about the bug's visible behavior in a separate test so the Blueprint remains a readable description of the test site.

Recommended CI example rules:

  • Commit blueprint.json and every local input it references.
  • Use exact WordPress.org versions and full Git commit SHAs.
  • Grant --blueprint-may-read-adjacent-files when a local JSON file intentionally reads sibling files. A directory input is shorthand for that JSON file and needs the same flag; a ZIP bundle does not.
  • Let the CLI validate the Blueprint before application-specific assertions.
  • Avoid network-dependent setup unless network behavior is itself under test.
  • Update a pin in a reviewable commit rather than silently following a branch.

See Run Blueprints v2 for browser, CLI, and JavaScript entry points.

You are done when​

  • The browser link loads without credentials or repository access.
  • The page states the steps, expected result, and actual result.
  • WordPress and dependency releases are pinned, the PHP runtime line is selected, and every Git source uses a full commit SHA.
  • Another person can reproduce the behavior from a fresh site without asking what to click.
  • The locked CLI runs the same Blueprint successfully in CI.

Security and failure reporting​

A reproduction can install and execute arbitrary plugin, theme, mu-plugin, PHP, SQL, or WP-CLI code. Review the example before running it, use a temporary site, and never store secrets in JSON or a share URL. The example keeps networkAccess: false; enable it only when outbound access is essential to the bug.

Blueprint execution is not transactional. If it fails halfway through, report the failing phase and source path, then retry on a fresh site. The troubleshooting guide follows the parse, validate, resolve, and execute phases in order.
